# Telegrama web client

Браузерний клієнт Telegrama без збірки: ASP.NET Core віддає файли з `wwwroot` на кореневій адресі сайту, тому клієнт і API живуть на **одному origin** (CORS не потрібен, refresh-cookie з `SameSite=Strict` працює як є).

```
wwwroot/
  index.html            розмітка + Content-Security-Policy
  css/styles.css
  js/app.js             уся логіка клієнта
  lib/signalr.min.js    @microsoft/signalr 8.0.7 (MIT), віддається з власного сервера, без CDN
```

## Запуск

```powershell
dotnet run --project .\Telegrama\Telegrama.csproj --launch-profile http
```

Відкрийте `http://localhost:5022/`. Журнал запитів і SignalR вмикається параметром `?debug=1` (тіла відповідей і тексти повідомлень туди не потрапляють).

## Що вміє клієнт

- **Автентифікація:** реєстрація, підтвердження email кодом, повторне надсилання коду з відліком 60 с, вхід, тихе оновлення сесії, вихід (разом у всіх вкладках).
- **Чати:** список із лічильниками непрочитаних і сортуванням за активністю, групи (Private / Public / OnlyLink), direct за тегом, приєднання за ID **або посиланням-запрошенням** (`/#join=<GUID>`), «позначити прочитаним» лише коли вкладка справді видима.
- **Повідомлення в реальному часі:** надсилання (Enter / Shift+Enter), **редагування** (✎ або ↑ у порожньому полі), **видалення**, індикатор «друкує…», розділювачі днів, кнопка «↓ Нові повідомлення», чернетки на кожен чат, лічильник символів (ліміт 2000).
- **E2EE для direct-чатів (експериментально):** браузер створює P-256 ECDH ключ, в IndexedDB зберігається приватний `CryptoKey`, а кожне повідомлення окремо шифрується AES-GCM. API зберігає та пересилає зашифрований конверт; сервер відхиляє незашифровані повідомлення в direct-чатах. Групові чати лишаються без E2EE.
- **Стійкість:** SignalR перепідключається необмежено (експоненційна затримка до 30 с); після розриву клієнт заново приєднується до кімнат і дозавантажує пропущені повідомлення; новий чат, створений іншим користувачем, з’являється протягом 30 с і одразу отримує повідомлення.

## Безпека

- Access JWT зберігається **лише в пам’яті**. Після перезавантаження сторінки його відновлює HttpOnly-cookie `telegrama_refresh` (`POST /api/users/session/refresh`). У `sessionStorage` / `localStorage` токени не потрапляють (у `localStorage` лежать тільки імена співрозмовників у direct-чатах).
- Увесь контент із сервера виводиться через `textContent`, `innerHTML` для даних не використовується.
- CSP: лише власні скрипти й стилі (`script-src 'self'`, `style-src 'self'`), без inline-коду і сторонніх CDN.
- Для E2EE потрібен secure context: HTTPS або `http://localhost`. Приватний ключ прив’язаний до браузерного профілю: очищення IndexedDB або інший пристрій поки не підтримуються, і старі повідомлення без E2EE не шифруються заднім числом.
- Ключі співрозмовників поки не мають механізму незалежної перевірки від підміни (fingerprint/QR), а протокол не має forward secrecy чи ratchet. Це навчальний прототип, не гарантія безпеки для чутливого листування.
- SignalR отримує токен через `accessTokenFactory` при кожному (пере)підключенні, тож після сну ноутбука чи розриву мережі використовується свіжий токен. Сам токен оновлюється заздалегідь (за хвилину до кінця життя, 15 хв) **без** перепідключення хаба.

## Розгортання в production

1. Секрети не зберігаються в репозиторії (`appsettings*.json` мають порожні значення). Передайте їх змінними середовища:
   `AuthSettings__SecretKey`, `AuthSettings__Issuer`, `AuthSettings__Audience`, `ConnectionStrings__DefaultConnection`, `EmailSettings__Host`, `EmailSettings__Port`, `EmailSettings__Email`, `EmailSettings__Password`.
2. Сайт має працювати по **HTTPS**: поза `Development` refresh-cookie ставиться з прапорцем `Secure`, по звичайному HTTP браузер її не збереже.
3. Якщо ASP.NET стоїть за reverse proxy (nginx, Traefik…), проксі має підтримувати WebSocket для `/hubs/chat` і передавати `X-Forwarded-Proto`.
4. `app.UseHttpsRedirection()` у `Program.cs` стоїть після `UseStaticFiles` / `MapHub`. Для production варто додати `UseHsts()` і переставити редірект на початок конвеєра.

## Відомі обмеження (на боці бекенда)

Клієнт обходить їх як може, але повністю вирішуються вони лише в API:

| Проблема | Як клієнт поводиться | Що варто змінити в API |
|---|---|---|
| Для direct-чату в БД зберігається назва «Заглушка», у списку немає співрозмовника | ім’я запам’ятовується локально (при створенні чату і за відправником в історії); поки співрозмовник нічого не написав, показується «Особистий чат» | повертати в `ChatDto` ім’я іншого учасника |
| `POST /api/chats/join-chat` не перевіряє тип чату | — | забороняти приєднання до `Private` і `Direct` без запрошення |
| Немає події про створення чату | список чатів опитується раз на 30 с та при поверненні на вкладку | надсилати через хаб подію `ChatCreated` |
| Історія без пагінації (останні 50–100) | показується максимум 100 останніх | параметр `before` у `last-messages` |
| Немає каталогу публічних груп | приєднання лише за ID або посиланням | endpoint пошуку публічних чатів |
